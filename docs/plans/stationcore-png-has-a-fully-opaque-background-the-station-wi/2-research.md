# Research

The question here is not a game-design one ("how do shipped games telegraph a boss?") — it is a
narrow asset-pipeline one with a specific, checkable answer. Research is scoped accordingly and
the findings below are the ones that actually change the plan.

| # | Finding | Tradeoff | Typical values / specifics | Source |
|---|---|---|---|---|
| 1 | **Flood fill from the border and global colour key differ exactly when the background colour also appears inside the artwork.** "Global removes every pixel of the selected color… Flood fill only removes connected pixels from where you click, useful when the same color appears in both the background and the sprite." A global key on such an image punches transparent holes through the subject. | Flood fill is strictly safer but leaves any background-coloured pocket that the artwork fully encloses. Global key is one pass and removes everything, at the price of holes you may not notice until the sprite is on screen. | `station_core.png` has **41 px** of `#565657` enclosed by the hull. Global key would punch 41 holes; flood fill leaves them, which is correct — an enclosed pocket of hull colour is hull, not sky. | [yomotherboard.com/pixel-art-background-remover](https://yomotherboard.com/pixel-art-background-remover/) |
| 2 | **Godot's importer already defends against the classic transparent-pixel fringe.** `process/fix_alpha_border` "fix[es] the edges of the image by painting invisible pixels the same color as the visible neighbours", which exists because editors leave stale RGB (usually white) under alpha 0 and "such white pixels end up showing thanks to texture filtering". Disabling mipmaps is the other half of the standard pixel-art fix. | Means we do **not** have to zero the RGB of the erased pixels — and arguably should not, since the importer will overwrite it with neighbour colours anyway, and preserving it keeps the PNG diff readable as "alpha changed". Costs nothing either way. | `station_core.png.import` already has `process/fix_alpha_border=true` and `mipmaps/generate=false`; `project.godot:175` sets `default_texture_filter=0` (Nearest). Three independent reasons there is no fringe here. | [Godot docs — Importing textures](https://docs.huihoo.com/godotengine/godot-docs/godot/tutorials/asset_pipeline/importing_textures.html), [Godot forum — black border on transparent sprite](https://forum.godotengine.org/t/black-border-on-transparent-sprite-3d-how-to-fix/109994) |
| 3 | **The root cause is a PixelLab default, and it is one flag.** `no_background` is an optional boolean on `create_image_pixflux`; passing `no_background=True` "returns the subject on a transparent background". It is *not* the default, and transparent generation "has a slightly higher cost than standard generation". | Regenerating correctly is cheap and easy **next time**; it does not help an asset already generated and already art-directed. It also means every future `create_image_pixflux` call in this repo must pass the flag explicitly or reproduce this exact bug. | The already-correct `station_turret.png` came from `create_map_object`, which is transparent by construction — which is why nobody had to ask for it. | [pixellab.ai — create-image-flux](https://www.pixellab.ai/docs/tools/create-image-flux), [pixellab.ai API](https://www.pixellab.ai/pixellab-api) |
| 4 | **PixelLab has a first-party "Remove background" tool, and we cannot use it.** It "automatically removes backgrounds from pixel art images", with Simple and Complex modes — but it is "available in Aseprite and Pixelorama extensions only", not through the web API. | Rules out the obvious "just call the vendor's tool" option. Confirms that doing the removal locally is not us reinventing an available API call; there is no API call. | Not present in this container's MCP tool list either (there is `inpaint_image`, `edit_image`, `correct_pixelart`, `reduce_colors`, `unzoom_image` — no background removal). | [pixellab.ai — remove-background](https://www.pixellab.ai/docs/tools/remove-background) |
| 5 | **Judgement call, no citable source:** 4-connected rather than 8-connected fill. 8-connected removes marginally more background but can leak through a single-pixel diagonal seam in the hull and eat the interior. 4-connected can only under-remove, never over-remove. | Under-removal is visible and fixable; over-removal destroys artwork and is only noticeable on screen. | Measured: 4-connected already reaches 34324/34365 background px (99.88%), so the theoretical extra coverage from 8-connected is at most 41 px, all of which are *enclosed* and should stay anyway. The safer algorithm costs nothing here. | — (labelled a judgement call) |

## What this rules in and out

- **Alpha-keying the existing art is viable and low-risk**, on findings 1, 2 and 5.
- **Regeneration is not necessary**, on finding 3 — the flag would have prevented the bug, but
  re-running it now discards art that four already-regenerated turrets were designed to match,
  spends a capped monthly allowance, and is not reversible.
- **There is no vendor API to call**, on finding 4.
